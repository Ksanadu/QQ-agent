# 回复等待窗口

机器人收到召唤后立即开始思考，纯 @ 也一样。**设置 → 聊天设置 → 回复等待窗口**（原 `wakeDelayMs`）决定何时最早能发出回复，已有设置不需要迁移。截止时间从唤醒者最后一条消息实际抵达的时刻算起；0 毫秒表示不额外等待。

先发内容再单独 @ 也可合并：纯 @ 新开主会话时，同一发送者在回复等待窗口内尚未交给主会话的文字、图片、语音和引用，按原顺序进入【本轮输入】。直接唤醒正在排队时同样适用；已有明确引用的召唤仍以该引用为准。窗口为 0 时不向前合并，其他群友、过期或已撤回的消息不进入当前请求。仅作历史背景的“已读”不等于“已处理”，实际纳入主会话的标记会落盘，避免重启后重复合并。思考仍立即开始，发送期限和启动等待耗时仍从 @ 的实际接收时间计算。

唤醒者续发的文字、图片、语音和引用留在同一个主会话，按接收顺序补进下一次模型请求。其他群友的消息不会延长本轮窗口：普通闲聊归入历史，直接召唤和监听确认的消息仍按自己的触发路径处理。主会话运行中，唤醒者再次纯 @ 只延长发送窗口，不另开会话。

查询类工具可以先执行。发送文字、图片、贴表情及其他有副作用的动作等到窗口结束，且模型已经读到最新补充时才执行。补充到达会淘汰尚未发出的旧稿；已经开始的外部操作仍按实际结果记账。只有最新一版请求的文字完整送达，才能正常完结。成功发送文字不会提前终止后续工具操作。

工具轮数不会因补充或重试而重置。一轮中至少有一次工具调用成功才扣一轮，全部失败不扣；被补充淘汰的旧稿不算“连续无进展”。真正连续三轮无进展或额度耗尽时，仍留一次仅发文字的交付机会。

最后交付机会又被新消息淘汰，或失败时仍有未处理的补充，宿主只把尚未处理的消息交给一个后续会话，原来的查询、发送和修改操作不重跑。引用、语音尚在入库的接收预留一并移交，不因补充没有 @ 而丢失。后续会话记录 `continuedFrom`；若它也失败，则保留待处理 ID 和错误，不无限开启新会话。

## 撤回与中止

撤回本轮请求、引用目标或已用于本轮判断的历史消息，会中断旧模型请求并禁止旧稿出站。还没有开始外部写操作时，按剩余有效消息重新组装上下文；全部请求已撤回则不回复。已经开始的发送或修改保留真实结果，不盲目重跑。历史工具、引用快照和后续提示词也会排除撤回内容；管理员存档保留原记录。

中止会取消在途模型、发送等待及只读查询。原生搜索、网页/图片下载、B 站和 Bangumi 查询使用会话取消信号；旧式只读插件的迟到结果会被丢弃。已经提交给 QQ 的发送继续核验回执，期间界面显示“正在中止…”，不会继续执行后续动作。

主会话的模型、工具、等待和重试共用一个总时限，默认 180 秒（配置 `sessionTimeoutMs`）。超过时限不再启动请求、切换模型或重试；已提交发送的回执核验不被截断。

## 独立关联监听

| 设置 | 配置字段 | 默认 |
| --- | --- | --- |
| 监听持续时间 | `conversationListener.idleMs` | 60 秒 |
| 判定前聚批 | `conversationListener.batchDelayMs` | 400 毫秒 |
| 判定后回复等待 | `conversationListener.wakeDelayMs` | 200 毫秒 |

主会话结束后才启动监听。主会话运行期间的其他候选消息先留存，结束后结合实际回复判断；中止主会话不会启动监听。判定前聚批仍是固定窗口，新消息不会重新计时。判定相关后，如果当前群没有主会话占用，立即开始思考；否则等当前主会话结束再交接。关联唤醒只使用自己的发送等待时长，不叠加普通回复等待窗口。监听选中的发送者续发时才会刷新该窗口。

## 验收

`npm run test:reply-lifecycle` 覆盖补充与撤回、失败分段修复、未确认回执、语音文字确认、中止与总时限、同群启动竞争；另用实际模拟 OneBot 撤回事件验收入站接线。`npm run test:wake-windows` 覆盖提前思考、窗口内补充、纯 @ 和监听交接；`npm run test:reply-trigger` 检查直接召唤，以及先发内容再 @ 的前置合并、媒体/引用/头像目标、排队和防重复边界；`npm run test:reply-completion` 和 `npm run test:delivery` 检查真实发送回执、完结和失败重试。
