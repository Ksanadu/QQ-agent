# 聊天功能扩展与分阶段验收（2026-10-25）

## Phase 1：历史搜索、连续任务

- `search_chat_history` 检索当前聊天保留的所有历史记录，支持关键词 AND、发送者 QQ/昵称、北京时间日期区间、分页、只找带图消息。
- 返回真实 QQ 消息 ID、发送者、时间、引用目标、图片数量；用现有消息详情/看图工具进一步读取。不会检索其他群或已撤回内容。
- 聊天结束后自动记住当前请求者的任务摘要与材料；多对象比较时模型可用 `set_task_context` 明确指定顺序。
- 任务按聊天和请求者隔离，保存 2 小时；新引用优先于旧任务。材料撤回后保留不可用的序号位置，不拿别的图片顶替。
- 验收：`node test/chat-history-tasks.mjs`，通过。覆盖窗口外历史、日期、分页、原始 ID、任务重启恢复、用户/群隔离、撤回与过期。

例：`找一下佬虎昨天推荐的游戏链接`、`按刚才的顺序，第二张再讲讲`。

## Phase 2：QQ 原生语音转文字

- 收到语音时调用 SnowLuma 的 `fetch_ptt_text({message_id})`，识别文本作为普通聊天材料进入主会话。
- 原生识别不可用时保留 `[语音]`，模型可用 `transcribe_voice_message` 重试；不下载音频、不装 Whisper、不新增本地 ASR 模型。
- 相同消息短时缓存，支持负数 QQ 消息 ID，重试只允许当前聊天的真实语音记录。
- 验收：`node test/qq-speech-test.mjs`，通过。真实事件→QQ 接口 mock→存档→主模型提示词链路、缓存、错误重试、跨群拒绝。
- 真机识别依赖 QQ 登录与 SnowLuma 在线；模拟测试不能替代真实账号的识别质量验证。

## Phase 3：图片收藏和检索

- `collect_chat_image` 保存指定消息的原图（多图使用从 1 开始的序号）、名称和内容标签；按图片内容哈希去重。
- `search_saved_images` 搜当前聊天图库；`get_saved_image` 查看；`send_saved_image` 发回已落盘的原图。
- 原图独立保存在数据目录，QQ 图片另外缓存中等规格预览。图片链接过期后仍可取回已收藏的文件。
- 只对主动收藏的图片写入图库，不后台扫描所有图片。未收藏的旧图仍可按时间、发送者和原消息文字搜索。
- 每会话最多 2000 张，单张下载上限 32 MiB；超限、非图片、非法 URL 明确失败并清理临时文件。图库内容和文件路径不提交 Git。
- 验收：`node test/image-album-test.mjs`，通过。保存/搜索/查看/发图、原始字节一致、重启、去重、多图、失败清理及会话/路径隔离。

例：`收藏这张，叫窗边白猫，标签加猫、午睡`、`把之前收藏的白猫发一下`。

## Phase 4：B 站视频卡片

- `share_bilibili_video` 接受 BV、av 或完整 B 站视频链接。名称、UP 主、封面从视频资料接口读取，不能由模型编造。
- 优先调用 QQ 的 `get_mini_app_ark(type=bili)` 生成卡片；接口不支持时生成 QQ 新闻样式的可点击 B 站 JSON 卡片。
- 通过现有发送队列、白名单、限频、去重、会话归属和发送回执逻辑交付。
- 短链接需先用已有 B 站查询工具解析到视频号。
- 验收：`node test/bilibili-card-test.mjs`，通过。视频 ID/URL 校验、资料失败处理、原生/兼容卡片、队列回执、存档及白名单拒绝。
- 真机卡片呈现效果取决于 QQ 客户端版本，mock 验证的是 JSON 段及发送链路。

## Phase 5：一分钟独立关联监听

- 群里触发主会话后，单开 Worker 线程作为监听子任务；同群同时最多一个。子任务有父会话 ID、判定依据和独立模型用量留档。
- 对新消息小批聚合后，让当前配置的 LLM 只做关联分类，不提供发送工具；只有实际新消息 ID 可被交回主会话。
- 确认是对机器人当前对话的承接才免 @ 回复。无关消息不续期；相关消息续期至其后 60 秒。没有消息时不轮询模型。
- 主会话运行期间的相关消息先排队，结束后串行处理；已处理消息不重复交付。
- 暂停、手动中止、停止应用或连续一分钟无相关消息时关闭线程；取消后的迟到判定不再唤醒主会话。
- 尊重会话白名单、群内指令禁言和主会话的 QQ 禁言检查。新监听开启时替代旧的“活跃期所有消息必响应”路径。
- 配置：`conversationListener.enabled` 默认 `true`，`idleMs` 默认 `60000`（最大一分钟）。关闭后恢复原有触发档位行为。
- 验收：`node test/conversation-listener-test.mjs`、`node test/conversation-listener-race.mjs`，均通过。覆盖实际 Worker+LLM mock+主会话、无关不回复不续期、免 @ 承接、子任务用量、超时、重启、主会话并发、去重、跨群和在途取消。

经用户指定，在管理员私聊实际发送 B 站小程序卡片、图库原图和约 4 秒的测试语音各一条。三条消息均取得 QQ 成功回执，随后 `get_msg` 读回的类型分别为 `json`、`image`、`record`。用户确认卡片和图片正常显示。

用户随后发来一条新的私聊语音。QQ-Agent 正常收到并调用原生识别，但 SnowLuma 首次返回 `ptt translate failed: error=9`，重试则返回“语音转文字超时（未收到结果推送）”。独立调用相同真实消息的 `fetch_ptt_text`，给予 25 秒客户端时限，仍在约 20,030 毫秒后收到协议端超时。因此语音转文字未通过真机验收，不能算完成功能；现有错误降级保留 `[语音]`，机器人会明确提示未识别。

监听已完成真实模型分类与完整一分钟计时验证；本轮发送位置仅获准为管理员私聊，未在真实群内发送免 @ 追问。群内主会话串行承接仍由前述端到端模拟测试覆盖。

### QQ 原生语音识别兼容修复

2026-10-25 补入 [SnowLuma 上游 76846f40 修复](https://github.com/SnowLuma/SnowLuma/commit/76846f40b141afec1a7d8a11673a1cca1d9ee0fd)：结果推送中的消息 ID 保留为 BigInt，以有符号 64 位形式生成等待键。旧代码先转 Number，会丢失负数 ID 的无符号 64 位表示，导致已收到识别文本仍等待超时。账号维度保持隔离。

- 本机 SnowLuma 1.14.20 已应用补丁并重启；原文件有校验过的独立备份。无需整体升级适配器。
- `node scripts/patch-snowluma-ptt.mjs [SnowLuma目录]` 可重复应用；`npm run setup` 也会检查。仅识别已知旧代码，未知版本原样保留并提示；已修复版本不会重复改写。
- QQ-Agent 的 HTTP 等待改为 25 秒，为适配器自身 20 秒识别窗口预留余量，使原生错误正常返回。
- 两条真实历史群语音（正、负 ID 各一条）均取得 QQ 原生识别文本；临时诊断确认两条均经过异步结果推送，负数 ID 成功匹配。清理诊断并重启后的正式版本复测分别约 208 / 198 毫秒成功。本次未在群内发送测试消息。
- 上次管理员私聊语音仍未识别成功；在 QQ 客户端直接点击“转文字”也显示“呃，什么都没有听到”。这证明该语音失败不限于 QQ-Agent，尚不足以推断所有私聊语音都可用或不可用。新的私聊语音验收待用户发送后继续。
- `npm run test:chat-features` 七项通过；新增测试覆盖相邻 64 位值、正负边界、跨账号隔离、已修复版本、未知版本、备份及实际旧运行时源码。临时协议诊断已移除；聊天内容、诊断日志、登录态与运行时二进制均未入库。

### 新私聊语音复验：未通过

用户随后发送新的约五秒管理员私聊语音。QQ-Agent 收到并尝试原生识别，仍出现 QQ `error=9`；独立重试也在约 20,027 毫秒后收到原生“未收到结果推送”超时。用户进一步在机器人登录的电脑 QQ 中直接点击同一条语音的“转文字”，确认客户端也无法识别。不能将这一结果归结为机器人消息 ID 匹配问题，也不能将群语音成功等同于私聊已恢复。

对照检查中，补齐其他实现的请求外层标记未使私聊成功，未纳入正式代码。保留已验证的无损 ID 兼容修复与 25 秒 HTTP 时限；移除临时协议诊断并恢复正式运行。当前验收结论：群语音原生识别通过；私聊原生识别仍失败，完整语音功能尚未通过验收。
